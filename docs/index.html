Executive Summary

Beyond Data Cloud & MCP ARI 2026 · Remediation + Build-Out

Summary

Beyond (BBY US, Overstock, BuyBuyBaby) runs mission-critical marketing and e-commerce operations across three brands. This scope fixes a live, undiagnosed MCP implementation while building a parallel Data 360 (Data Cloud) foundation to feed enriched, unified customer data into MCP and paid-media activation. Two concurrent tracks — MCP Next remediation and Data 360 build-out — on a shared 24-week waterfall calendar. The program adds Acxiom enrichment, 5 ad-platform connectors, web experience personalization, and Braze integration. The aim is a low-disruption, high-confidence remediation that upgrades Beyond's Salesforce footprint without service disruption.

G0002Potential RiskThe Acxiom enrichment set includes sensitive-adjacent attributes (estimated income, presence/age of children, marital status, home value, move date) used for targeting, including a mortgage-interest use case. No compliance or regulatory framework (CCPA, state privacy law, retention/consent/suppression requirements beyond one SHA-256-hashed suppression field) is discussed in the source material.
G0004Missing RequirementIs governance / Center of Excellence / change management in scope, or assumed handled client-side? No mention of a CoE, training plan, or adoption/change plan for the teams operating MCP and Data 360 post-launch — who owns ongoing campaign management and data-attribute governance after go-live?
G0202Missing RequirementNo per-table sync method has been decided for the 4 Customer Data Mesh tables (bi_customer_account, bi_customer_storefront, bi_visit, bi_email_daily_summary). The epic description leaves 'Zero Copy, ingestion, or a hybrid pattern' fully open with no table-by-table assignment.
G0203Potential RiskZero Copy data streams against Google BigQuery are capped at 10GB or 100 million rows before timeout/job-execution errors (EXEC_JOB_EXEC_ERR). bi_visit and bi_email_daily_summary are the two tables most likely to be high-volume, multi-year activity data across 3 brands.
G0204Potential RiskZero Copy Data Federation does not support record deletion during incremental refresh — only ingestion-based Data Lake Objects support a delete-flag pattern. This conflicts with the one confirmed suppression field already in scope (the Acxiom DMA-suppression attribute) and any future consent-revocation/right-to-be-forgotten handling on BigQuery-sourced customer records.
G0206Missing RequirementNo identity resolution / unified-profile strategy has been defined across the three in-scope brand domains (BBY US, Overstock, BuyBuyBaby). The 4 BigQuery tables carry account/storefront/visit/email data that may represent the same underlying customer shopping across brands, and the Acxiom enrichment is keyed per Person ID — but nothing in the source material defines matching/reconciliation rules to actually unify a cross-brand customer record.
G0207Missing RequirementGovernance / data-stewardship question for the client: no stewardship model has been defined between whichever team owns and changes the BigQuery schema (presumably Beyond's internal data/BI engineering team) and the Data 360 delivery team consuming it. Who on Beyond's side owns the BigQuery schema contract with Data 360, and what's the process when a column is renamed, a type changes, or a new table is added?
G0208Missing RequirementNo credit/consumption sizing has been modeled against expected row volumes. Zero Copy Federation live-query access consumes credits at roughly 70 per million rows accessed (more again for private-connection ingestion of the same federation), and canonical ingestion consumes separate Batch/Streaming Data Ingestion credit types — but none of this has been sized against the actual row counts of 3 brands' account, storefront, visit, and daily-email-summary data.
G0209Potential RiskZero Copy connections to BigQuery behave differently in sandbox vs. production (documented sandbox-specific constraints), and the engagement's SIT/UAT phases (per the schedule in the estimate) aren't described anywhere as having a BigQuery test-data or lower-environment connectivity strategy.
G0301Source ConflictThe source attribute table backing the '~39-attribute' Acxiom set contains duplicate rows: #9 and #11 are both household.coreDemographicsIncomeFullCoverage.estimatedIncome.narrowRanges.precisionLevel, and #14 and #16 are both household.interestGroupings.homeImprovement. The true unique-attribute count appears to be ~37, not 39.
G0304Missing RequirementNo ingestion method, connector choice, or refresh cadence for the Acxiom feed into Data 360 is confirmed with the client or with Acxiom. Is the feed delivered as a scheduled batch file (SFTP/flat file via Ingestion API) or a programmatic API pull, and how often does it refresh (monthly, quarterly)?
